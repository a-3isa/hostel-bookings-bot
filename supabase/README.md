# supabase/

> **RETIRED 2026-10-12.** The bot no longer reads or writes this. The admin edits the sheet by hand and never uses the dashboard, so this data went stale, and a bot that read it wrote payments onto the wrong guest's row. Kept for reference only; nothing in `booking_bot/` depends on it, and running `backfill.py`, `reindex.py` or `mirror.py` no longer has any effect on the bot.

The Postgres side of the bot. **Not live yet** — nothing in `booking_bot/` talks
to it. See [`../docs/2026-08-08-supabase-migration-scope.md`](../docs/2026-08-08-supabase-migration-scope.md)
for the plan and the reasoning.

| File | What it is |
|---|---|
| `schema.sql` | Full DDL. Safe to re-run — every statement is `if not exists` / `or replace`. |
| `backfill.py` | Reads the spreadsheet, emits idempotent upserts. Read-only against Google. |
| `seed.sql` | Generated by `backfill.py`; regenerate rather than edit. |

## Running it

```bash
python supabase/backfill.py --out supabase/seed.sql   # no database needed
python supabase/backfill.py --apply                   # needs SUPABASE_DB_URL
python supabase/backfill.py --reconcile               # compare db against the sheet
```

`SUPABASE_DB_URL` is the **connection pooler** URI from Supabase → Project
Settings → Database, in the form
`postgresql://postgres.<ref>:<password>@<region>.pooler.supabase.com:6543/postgres`.
Put it in `.env`, which is gitignored. `--apply` and `--reconcile` also need
`pip install 'psycopg[binary]'`.

## Why the schema is so permissive

It has to accept everything the spreadsheet already accepts, or dual-write starts
failing on real bookings. Measured against the 46 live rows on 2026-08-08:

- row 9 has a guest and 3000 outstanding, but no room, no apartment, no arrival;
- 3 rows have no ID;
- guest refs `5` and `16` each appear on two different bookings.

So `room_id`, `arrival` and `guest_ref` are all nullable and none are unique.
Constraints get tightened at the flip, on cleaned data — not now.

For the same reason **double-booking is a view, not an exclusion constraint**.
The bot warns about a clash and lets the receptionist override it; a constraint
would reject a booking the sheet had already accepted, and dual-write would fail
on a real guest. `booking_overlaps` reports the same thing and cannot break
anything. The constraint to swap in at the flip is written out in `schema.sql`.

## Hand-entered formulas

People type formulas into the columns the bot writes, and the backfill preserves
the intent rather than flattening it:

- `=500*I{row}` in اجمالي سعر الحجز is a **nightly rate** — parsed into
  `nightly_rate` (rows 10, 11, 17 at 500; row 29 at 700). For an open-ended stay
  the bill has to keep growing, which is what the `bookings_live` view does.
- `=2000+225` in اجمالي ما تم دفعه is just arithmetic; the evaluated total is the
  whole meaning, so it is imported as a number.
- Row 32 is `=940*2+650*8` — two rates across one stay, which no single
  `nightly_rate` can express. The value is kept, the text is preserved in
  `total_formula`, and the backfill **flags it**, because that booking is
  open-ended and its total has therefore stopped tracking nights *in the
  spreadsheet too*. Someone needs to decide its rate.

## Read `bookings_live`, not `bookings`

`total` and `remaining` on the base table are the stored figures. For an
open-ended stay with a nightly rate the real numbers grow every night, and a
generated column may not reference `current_date`. `bookings_live` adds
`effective_nights`, `effective_total` and `effective_remaining`. Anything shown
to a person should come from there.
